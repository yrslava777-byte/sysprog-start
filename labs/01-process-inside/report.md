# ЛР 1. Процесс изнутри

Система: macOS 26.6.2 (25G83), arm64 · компилятор: Apple clang version 21.0.0 (clang-2100.1.1.101)

## Программа на C
Программа напечатала PID 83922, монитор показал PID 83922.
Память процесса в мониторе: физическая — 592 КБ, собственная — 16 КБ, совместная — 720 КБ, виртуальная — 415,13 ГБ. Процессорное время: 0,00 с; при повторном наблюдении не увеличилось. Один поток, загрузка ЦП — 0,0 %.
Пока программа ждёт Enter, процессорное время не растёт, потому что чтение в getchar блокируется: ядро переводит процесс в ожидание ввода; активного цикла ожидания нет.
Дескрипторов у процесса: 3 (0 — stdin, 1 — stdout, 2 — stderr). Ввод и вывод ведут в /dev/ttys000. В мониторе также видны рабочая папка, исполняемый файл hello и загрузчик /usr/lib/dyld; это не дополнительные числовые дескрипторы приложения.
Системные библиотеки в процессе: 44 файла .dylib по __TEXT в vmmap; среди них /usr/lib/libSystem.B.dylib, /usr/lib/system/libsystem_c.dylib, /usr/lib/system/libsystem_kernel.dylib, /usr/lib/system/libsystem_malloc.dylib, /usr/lib/system/libdyld.dylib.
После завершения из монитора терминал напечатал «exit code: 143», код завершения 143. Выбрано «Завершить», а не «Завершить принудительно»: сигнал SIGTERM имеет номер 15, 128 + 15 = 143. Процесс исчез из монитора и не дошёл до return 0.

## Программа на Python
Имя процесса в мониторе: python.exe, PID 90915, память — физическая 4,3 МБ, собственная 1 008 КБ, совместная 736 КБ. Время ЦП — 0,04 с, один поток.
Памяти больше, чем у программы на C, примерно в 7,3 раза (4,3 МБ / 0,592 МБ, по округлённым значениям физической памяти монитора).
Общая библиотека у программ на C и Python: /usr/lib/libSystem.B.dylib. В карте памяти Python также найден _ctypes.cpython-314-darwin.so, через который вызывается getpid.
Код завершения при обычном выходе: 0; после Enter терминал напечатал «exit code: 0». Скрипт дошёл до конца без ошибки, в отличие от завершённого снаружи C-процесса с кодом 143.

Использован Python 3.14.0, собранный из официальных исходников python.org в рабочей папке. Имя python.exe — имя результата этой сборки на macOS; это нативный процесс Apple Silicon, а не программа Windows. Скрипт hello.py интерпретатор читает как данные.

## Помощник ИИ (Р1)
Запрос: «Объясни программу hello.c по строкам». Одно место, где ответ точнее или менее точен, чем глава 0.1: глава описывает getchar() как ожидание Enter; объяснение ИИ уточняет, что getchar читает один символ stdin, а ожидание Enter связано с каноническим режимом терминала. При уже подготовленном вводе или EOF ожидания Enter не будет. В данном опыте stdin подключён к терминалу, поэтому наблюдалось ожидание.

Не получилось: невыполненных шагов лабораторной нет; программы запущены, PID сверены, память, дескрипторы и библиотеки исследованы, оба способа завершения проверены.
ИИ: использовал для объяснения исходного кода, выполнения команд, сверки показателей Мониторинга системы, заполнения отчёта по реальным измерениям и запуска проверок преподавателя.
